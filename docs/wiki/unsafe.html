Unsafe Blocks

Ume is memory-safe by default, but it provides an escape hatch for cases where you need raw pointer manipulation, manual memory management, or direct C++ interop. These operations are confined to unsafe blocks so that the rest of your code can rely on the safety guarantees.

unsafe block syntax

The unsafe keyword introduces a block (in braces) inside which pointer operations, alloc, free, dereference, and address-of are legal. Outside an unsafe block, these operations are rejected at compile time. The block doesn't change runtime behavior — it's a compile-time gate that confines dangerous operations to clearly-marked regions.

unsafe {
    int* ptr = alloc<int>();
    *ptr = 42;
    Console.println(*ptr);   // 42
    free(ptr);
}

alloc<T> and free

alloc<T>(count) allocates a contiguous block of memory big enough for count values of type T and returns a T* pointing at the start. If you omit the count, it defaults to 1. The memory is not initialized. free(ptr) releases the memory; the pointer is then invalid and must not be used again.

unsafe {
    // Allocate space for 1024 bytes
    byte* buf = alloc<byte>(1024);

    // Use the buffer...
    buf[0] = 0xFF;
    buf[1] = 0xAA;

    // Release it
    free(buf);
}

This is raw heap memory with no automatic cleanup — you are responsible for calling free exactly once per allocation. Forgetting to free causes a memory leak; freeing twice or using freed memory causes undefined behavior. There is no garbage collector for alloc'd memory.

Pointer types T*

A pointer holds the address of a value of type T. Pointers can be stacked (int** is a pointer to a pointer to int). They're declared by appending * to a type, and multiple *s stack. Pointers are only usable inside unsafe blocks.

unsafe {
    int*  p;        // pointer to int
    int** pp;       // pointer to pointer to int
    byte* bytes;    // pointer to byte
}

Dereference *ptr

The prefix * operator reads or writes the value a pointer points at. On the left of an assignment it stores a new value; in an expression it reads the current value.

unsafe {
    int* p = alloc<int>();
    *p = 100;          // store 100 at the address p points to
    int v = *p;        // read the value back
    Console.println(v);   // 100
    free(p);
}

Address-of &value

The prefix & operator yields a pointer to an existing variable. This lets you obtain a pointer without allocating — the pointer aliases the variable's storage. Modifying through the pointer affects the original variable, and vice versa.

int value = 99;

unsafe {
    int* p = &value;
    *p = 200;          // modifies 'value' through the pointer
}

Console.println(value);   // 200
Dangling pointers

Be careful with & on local variables. If you store the pointer somewhere and the local goes out of scope, the pointer becomes dangling — using it is undefined behavior. Only take the address of locals whose lifetime you can guarantee exceeds the pointer's use.

Pointer indexing

You can index a pointer with [] as if it were an array. ptr[i] is equivalent to *(ptr + i) — it accesses the i-th value past the pointer. This is the standard way to work with alloc'd buffers:

unsafe {
    double* arr = alloc<double>(5);
    arr[0] = 1.0;
    arr[1] = 2.0;
    arr[2] = 3.0;
    arr[3] = 4.0;
    arr[4] = 5.0;

    double sum = 0.0;
    for (int i = 0; i < 5; i++) {
        sum += arr[i];
    }
    Console.println(sum);   // 15.0

    free(arr);
}

C++ interop

Unsafe blocks are also the boundary for calling into C++ code that Ume's runtime doesn't natively wrap. The exact interop mechanism depends on the runtime bindings available in your build; the general principle is that any operation involving raw addresses, manual memory, or unmanaged resources belongs in unsafe.

When to use unsafe

The standard library already covers most common needs safely: List<T> instead of manual buffers, Map<K,V> instead of pointer-based lookup tables, File instead of raw file descriptors. Reach for unsafe only when:

  • You're implementing a low-level data structure (a custom allocator, a ring buffer) and need raw memory control.
  • You're interfacing with a C/C++ library that exposes pointer-based APIs.
  • You have a proven performance bottleneck that manual memory management would resolve, and you've measured it.
Use sparingly

Unsafe code bypasses Ume's safety guarantees. A single dangling pointer or double-free can corrupt memory in ways that are extremely hard to debug. Keep unsafe regions small and well-tested, and prefer the safe standard library whenever possible.
