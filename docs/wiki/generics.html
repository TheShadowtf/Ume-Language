Generics

Generics let you write code that works over any type while keeping full static type safety. A List<int> and a List<string> share the same code but the compiler knows their element types are different — you can't add a string to a List<int>.

Generic classes

A class can take one or more type parameters, listed in angle brackets after the class name. Inside the class body, the type parameters can be used anywhere a regular type would: as field types, parameter types, return types, or local variable types.

public class Box<T> {
    private T value;

    public Box(T v) { value = v; }

    public func T get() { return value; }
    public func void set(T v) { value = v; }
}

var intBox = new Box<int>(42);
var strBox = new Box<string>("hello");

Console.println(intBox.get());   // 42
Console.println(strBox.get());   // hello

// intBox.set("oops");   // ← compile error: wrong type

Multiple type parameters

A generic class can take several type parameters, separated by commas. The standard library's Map<K, V> is a good example.

public class Pair<A, B> {
    public A first;
    public B second;

    public Pair(A a, B b) { first = a; second = b; }
}

var p = new Pair<string, int>("Alice", 30);
Console.println(p.first);   // Alice
Console.println(p.second);  // 30

Generic methods

Methods and free functions can also be generic. Type parameters go in angle brackets before the function name. The compiler can often infer them from the arguments, but you can specify them explicitly when needed.

// T is a type parameter
public func T identity<T>(T x) {
    return x;
}

int    n = identity(42);            // T inferred as int
string s = identity("hi");         // T inferred as string

// Generic function with two type params
public func Pair<A, B> makePair<A, B>(A a, B b) {
    return new Pair<A, B>(a, b);
}

var p = makePair("Alice", 30);     // inferred: Pair<string, int>

Generic methods on generic classes

A method on a generic class can introduce additional type parameters of its own. This is how List<T>.map<R>() works: T comes from the class, R is introduced by the method.

public class List<T> {
    // ...
    public func List<R> map<R>(func R (T) transform) {
        var result = new List<R>();
        foreach (T item in this) {
            result.add(transform(item));
        }
        return result;
    }
}

List<int>  nums    = [1, 2, 3, 4, 5];
List<int>  doubled = nums.map(n -> n * 2);          // T=int, R=int (inferred)
List<string> words = nums.map(n -> $"num {n}");        // T=int, R=string (inferred)

Specifying type arguments at construction

When you construct an instance of a generic class, you provide the type arguments in angle brackets after the class name. This fixes the type parameters for that instance. For generic methods, type arguments are usually inferred from context — you can omit them:

// Generic method — type inferred (preferred):
var n = identity(42);        // T = int
var s = identity("hi");     // T = string

// Generic method — explicit type args (also works, but verbose):
// var n = identity<int>(42);  // explicit, but may not parse in all versions

var ints    = new List<int>();
var strings = new List<string>();
var pairs   = new List<Pair<string, int>>();

ints.add(1);       // OK
// ints.add("x");  // error



Generic interfaces


Interfaces can be generic too, with the same syntax. See Interfaces → Generic interfaces for an example using Comparable<T>.



Why generics matter


Without generics you'd have two bad options: write a separate IntList, StringList, etc. for every element type (lots of duplicated code), or use List<any> and lose type safety (the compiler can't stop you from putting a string into a list of integers). Generics give you both reuse and safety — write the list code once, parameterize it by element type, and the compiler enforces the types at every use site.




  
Type erasure

  
Ume generics are not implemented by type erasure. Different instantiations of a generic class produce different C++ types in the transpiled output, so Box<int> and Box<string> are genuinely distinct types at runtime — you cannot cast between them.





Type constraints


Currently Ume does not enforce explicit type constraints (like T extends Comparable) on type parameters. Type parameters are treated as any-like — you can call any method on a value of type T, and the call is checked dynamically. This is less safe than bounded generics but more flexible; treat it as a known limitation when designing APIs.
