Exceptions

Exceptions are Ume's mechanism for signaling and recovering from runtime errors. The try/catch/finally/throw quadruple works just as in C# or Java — you wrap risky code in try, handle failures in catch, and clean up in finally.

throw

The throw statement raises an exception. It must be followed by an expression that evaluates to an Exception instance. When throw executes, the current function exits immediately and the runtime walks up the call stack looking for a matching catch. If none is found, the program terminates with an unhandled-exception error.

func int divide(int a, int b) {
    if (b == 0) {
        throw new Exception("Division by zero");
    }
    return a / b;
}

try / catch

Wrap code that might throw in a try block. Follow it with one or more catch clauses, each catching a specific exception type. When an exception is thrown inside the try, the runtime walks the catch clauses in order and runs the first one whose type matches. The caught exception is bound to the variable you name in the catch (Type name) clause.

try {
    Console.println(divide(10, 0));
} catch (Exception e) {
    Console.println("Error: " + e.getMessage());
}

Multiple catch clauses

You can have several catch clauses, each handling a different exception type. They're tried in order — put the most specific types first, because the first match wins. A general Exception catch at the end acts as a catch-all.

public class ValidationError extends Exception {
    public string field;
    public ValidationError(string field, string msg) {
        super(msg);
        this.field = field;
    }
}

try {
    throw new ValidationError("email", "Invalid email format");
} catch (ValidationError ve) {
    Console.println("Validation failed on '" + ve.field + "': " + ve.getMessage());
} catch (Exception ex) {
    Console.println("Generic error: " + ex.getMessage());
}

finally

A finally block runs no matter what — whether the try completed normally, threw an exception that was caught, or threw an exception that wasn't caught (in which case finally runs and then the exception propagates). Use finally for cleanup that must always happen: closing files, releasing locks, restoring state.

Mutex m = new Mutex();
m.lock();
try {
    // critical section
    doWork();
} catch (Exception e) {
    Console.println("work failed: " + e.getMessage());
} finally {
    m.unlock();   // always runs — even if doWork threw
}

The Exception class

The base Exception class is provided by the prelude and is always available without an import. It has a message field (a string) and two accessors:

MemberDescription
messagePublic field holding the error description.
getMessage()Returns the message string.
toString()Returns the message string (alias for getMessage).

Construct an Exception with new Exception("message"). The constructor stores the message in the message field.

Custom exception types

Extend Exception to create your own exception types. Call super(message) in your constructor to set the base message, then add any extra fields your exception needs. Custom exceptions let you carry structured error information and let callers catch specifically your error type rather than any Exception.

public class FileNotFoundError extends Exception {
    public string path;
    public FileNotFoundError(string path) {
        super("File not found: " + path);
        this.path = path;
        this.message = "File not found: " + path;  // explicitly set for getMessage()
    }
}

try {
    throw new FileNotFoundError("/etc/config");
} catch (FileNotFoundError e) {
    Console.println("Missing: " + e.path);
    Console.println("Message: " + e.getMessage());
}

Exception hierarchy

Since custom exceptions extend Exception, a catch (Exception e) clause catches them too. This is why the catch-all Exception clause goes last in a multi-catch block — otherwise it would shadow the more specific types below it. You can build deeper hierarchies (AppError extends Exception, NetworkError extends AppError, TimeoutError extends NetworkError) and catch at whichever level of specificity you need.

Re-throwing

Inside a catch block you can throw again — either the same exception you caught or a different one. This is useful for logging and rethrowing, or for wrapping a low-level error in a higher-level one:

try {
    riskyOperation();
} catch (Exception e) {
    Console.println("logging: " + e.getMessage());
    throw new Exception("higher-level failure", e);   // wrap and rethrow
}
Exceptions for exceptional cases

Exceptions are for exceptional conditions — things that go wrong unexpectedly. Don't use them for normal control flow (like ending a loop or returning a value), because they're slower than a normal return and they obscure the happy path. If a failure is an expected outcome that callers will routinely check for, prefer returning a nullable or a result value.
