Modules & Imports

Ume has two independent mechanisms for bringing external code into a file: an AST-level import statement that resolves packages by name (Java/C# style), and a C-style #include preprocessor directive that textually splices a file's source. This page covers both, in full.

The two mechanisms at a glance

Both let you reuse code across files, but they operate at completely different stages of the pipeline and have very different semantics. Understanding the difference matters because mixing them up is the most common source of "why can't the compiler find my symbol" bugs.

Declaring a package

A package declaration at the top of a .ume file gives that file a logical module name. The name can be dotted. The package resolver scans every .ume file under your project's search paths (the current directory, the directory of the entry file, and any -I include paths) and builds a map from package name → file. When you later write import mypkg, the resolver looks the name up in that map — it does not care about the file's location on disk, only its declared package name.

package MyApp;

public class Greeter {
    public func string hello(string name) {
        return $"Hello, {name}!";
    }
}

The namespace keyword works the same way and is interchangeable for the purpose of imports — namespace is provided as a keyword for developers coming from C++/Kotlin. The resolver treats both identically when scanning.

// File-level — same as `package MyApp;`
namespace MyApp;

// Block-level — groups several declarations under one name
namespace MyApp.Models {
    public class User {
        public int id;
        public string name;
    }
}

When using a block-level namespace, the resolver recurses into the block and registers every top-level declaration inside it as belonging to that namespace. So User above is reachable as MyApp.Models.User.

Automatic file discovery

You do not need to place files in rigid directory layouts that mirror the package name. The resolver scans the whole project tree for package/namespace declarations, so a file declaring package MyApp.Models; can live anywhere — even flat in src/. The name is what matters, not the path.

Importing symbols with import

The import statement is the primary way to reference code from other packages. There are three forms.

Selective symbol import

Import only one specific class, function, struct, enum, or interface from a package. Other declarations in that package are not pulled in and cannot be referenced unless you import them too. This keeps your file's scope clean.

package Main;

import MyApp.Models.User;   // only User is brought in

public class Main {
    public static func void main() {
        var u = new User();
        u.id   = 1;
        u.name = "Alice";
        Console.println(u.name);
    }
}

Wildcard import

Import all public declarations from a package. Convenient for quick scripts and when you genuinely want everything.

import std.collections.*;
import std.thread.*;
import std.math.*;

public class Main {
    public static func void main() {
        var nums = new List<int>();
        var m    = new Mutex();
        var pi   = Math.PI;
    }
}

Whole-module import

If you write import pkg; without a trailing symbol or wildcard, the resolver loads the package file and injects its declarations, but they're referenced through the package path rather than dumped into your scope. This form is rarely used directly — selective and wildcard imports cover almost all real cases.

import MyApp.Models;

public class Main {
    public static func void main() {
        var u = new MyApp.Models.User();
    }
}

String-form import

You can also pass the import path as a string literal. This is occasionally useful when the package name contains characters that would otherwise need escaping, but it's uncommon.

import "MyApp.Models.User";

Textual inclusion with #include

#include is a preprocessor directive. Before the lexer even sees your source, the preprocessor scans for #include lines, reads the named file, and pastes its contents verbatim into your source at that point. This is exactly how C/C++ #include works. There is no symbol resolution — the included file's tokens become your tokens.

The delimiter controls where the resolver looks for the file:

FormSearch location
#include "path.ume"Relative to the current file's directory first, then the configured include paths.
#include <path.ume>Relative to the Ume standard library directory (stdlib/) and system include paths only.
 
// Pull in a shared config file next to this one
#include "config.ume"

// Pull in something from the stdlib tree
#include <io.ume>

public class Main {
    public static func void main() {
        // config.ume's contents are now part of this file
        Console.println(GREETING);
    }
}

Include guards

The preprocessor tracks every file it has already included by absolute path. If you #include the same file twice (directly or transitively), the second and subsequent includes are silently skipped. This means you don't need manual #pragma once-style guards — Ume handles it for you. It also means #include is idempotent, which is important for cyclic or diamond-shaped include graphs.

When to use which

Use import for application code and library APIs — it gives you symbol isolation, wildcard convenience, and works regardless of file location. Reserve #include for cases where you genuinely want raw text splicing: shared constant blocks, code-generation templates, or C-style header idioms. For everyday work, import is almost always the right choice.

How the resolver finds a package

When the compiler sees import a.b.c, the package resolver tries several strategies in order until one succeeds. Knowing this order helps debug "unresolved import" errors.

  1. Exact package map match. If any scanned file declares package a.b.c;, that file is used.
  2. Dotted split. Split into a.b (package) + c (symbol). If a file declares package a.b;, load it and pull out only c.
  3. Filesystem match. Convert dots to slashes (a/b/c) and look for a/b/c.ume or a/b/c/package.ume in each search path.
  4. Symbol split on filesystem. Same as #2 but applied to the filesystem: look for a/b.ume and treat c as the symbol.
  5. Bare filename. If all else fails, treat the whole thing as a filename and look for it directly (e.g. math.ume).

The search paths tried are: the current file's directory, then every -I path, then the current working directory. The standard library directory is always searched.

Standard library imports

The bundled standard library lives in the stdlib/ directory and is organized into packages. Each file declares its own package name (for example, collections.ume declares package std.collections;).

Every standard library module can be brought in two ways:

Always available (no import needed)

The following are natively backed by the interpreter and are always in scope — no import or #include required:

  • Console — println, print, readLine, WriteLine, Write, clear
  • Math — basic functions (PI, sqrt, pow, abs, floor, ceil, round, sin, cos, tan, log, log10, min, max, clamp)
  • range(), rangeTo(), repeat() — prelude helper functions
  • Pair, StringBuilder — prelude classes (natively backed)
  • Thread.sleep() — static method

What's auto-loaded (the prelude)

A few things are always available without any import. The prelude.ume file is automatically loaded by the runtime before your code runs. It provides the base Exception class, a generic-any Stack and Queue (the older pre-generics versions), Pair, the range() and repeat() helper functions, and a pre-generics StringBuilder. The core Console and basic Math (PI, sqrt, sin, cos, …) classes are natively backed by the C++ runtime and are also always available. See Core (Prelude) for the full list.

A complete multi-file example

Here's a small project showing both mechanisms in use. The math helpers use the package system (selective import), and a shared constants file uses #include.

math_tools.ume

namespace MyMath;

public func int add(int a, int b) {
    return a + b;
}

public func int multiply(int a, int b) {
    return a * b;
}

config.ume (textually included)

// These constants get pasted into main.ume verbatim
const int MAX_RETRIES = 3;
const string APP_NAME = "demo";

main.ume

package App;

#include "config.ume"            // textual include — MAX_RETRIES, APP_NAME now in scope
import MyMath.add;               // selective import — only add(), not multiply()

public class Main {
    public static func void main() {
        int sum = add(10, 20);       // works — add was imported
        // int prod = multiply(10, 20);  // ERROR — multiply was not imported

        Console.println($"{APP_NAME}: sum = {sum}, retries = {MAX_RETRIES}");
    }
}
